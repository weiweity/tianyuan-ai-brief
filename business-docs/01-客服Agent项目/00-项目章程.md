### 1.2 名称边界

“客服 Agent”是项目名称，不等于首期建设完整自治 Agent。

一期只验证：

1. 一个真实、高频、损失明确的客服任务能否被软件有效改善；
2. 坐席能否少切换、少查找、少出错，同时保留人工判断；
3. 系统没有可靠依据时，能否明确说“不知道”并回到人工流程；
4. 权威内容变更、下架和恢复是否有人负责、可以追溯；
5. 3～5 名坐席真实使用两周后，证据是否支持扩大、整改或停止。

自动代回、四个方向一起做、所有平台一次接完、外包全量接入和复杂自治 Agent 都不属于一期。

### 1.3 已批准什么，还没有批准什么

公司已经批准“启动客服 Agent 项目并进入需求与方案阶段”，公开仓登记为 `EVD-CUSTOMER-APPROVAL-20260801`。这不代表一期功能、费用、数据权限、技术栈和上线时间已经批准。开发前总检查（G0）仍需补齐：

- 客服业务 Owner、内容 / 话术 Owner、预算责任人、IT / 安全责任人；
- A / B / C 费用路径及对应执行边界；
- 数据、安全、部署、运行和回退批准。

## 2. 背景与问题

受控证据 `EVD-CUSTOMER-INTERVIEW-20260722` 记录了智能质检、评价分析报告和聊天分析等诉求；知识/话术辅助也可能是一个方向。但现在不能只凭功能名称决定一期做什么。

08-04 由客服总监、经理、客服 BP、内容 / 话术负责人候选和至少 3 名坐席共同看真实工作：任务从哪里来、在哪个平台处理、哪里耗时、哪里出错、何时升级、最终怎样算处理完成。四个方向只作为讨论起点，可以形成先后顺序，不做“谁票多就先做”的功能投票。

一期主问题必须同时满足：真实发生、有分母和基线、软件能在较短时间形成最小闭环、风险可控、两周灰度可以证伪。若证据不足，会议结论就是“补证”，不能用现有页面强行锁定某个功能。

## 3. 目标与成功定义

### 3.1 目标

建设一个内部可访问、有人负责、能监控、能回退的客服 Agent 一期软件，只解决 08-04 冻结的一个主任务。系统帮助坐席完成工作，但不替坐席发送、不替业务负责人决定正确答案，也不把点击次数包装成业务价值。

### 3.2 一期成功标准

| 维度 | 首期门槛 |
|------|----------|
| 问题适配 | 主任务有真实样本、发生频次、现状耗时 / 错误 / 升级和经营影响；同时保留“不上新软件”的对照办法 |
| 内容资产 | 若主任务涉及知识 / 话术，权威来源、Owner、版本、适用平台 / 场景、有效期与冲突规则全部清楚 |
| 上线前冒烟 | 若主任务涉及检索，冻结 20 条正例全量盲测，Top3 命中率 ≥70%；不少于 5 条负例，错误直答 = 0；该门槛不单独证明业务成功 |
| 证据与追溯 | 每次系统辅助都能回到对应任务证据；若涉及知识 / 话术，引用 / 版本正确率 = 100%，并可追溯到内容 ID、版本与来源 |
| 真实采用 | 3～5 名内部坐席连续两周，每人每周 ≥5 个去重真实任务 |
| 效果指标 | 质量、端到端处理时长、采用 / 大幅修改 / 拒绝、未命中、升级、稳定性都报原始计数和比例，不以搜索次数单独通过 |
| 人在环 | 自动代发次数 = 0；无可靠依据时拒答或转人工 |
| 内容治理 | 草稿 → 复核 → 发布 / 下架 → 回滚链路可用且有审计记录 |
| 项目结论 | 只能形成扩大、一次限时整改后重测、停止三种书面决定 |

指标可以在 G0 根据基线调整；一经签发，变更必须进入 CR / DEC 并整集重测。

## 4. 范围

### 4.1 In Scope

| 能力 | 一期最小范围 |
|------|----------------|
| 主任务 | 只做 08-04 冻结的一个高频任务；有原流程和零新增软件对照 |
| 坐席端 | 当前任务、候选建议、来源、适用范围、人工插入 / 编辑 / 拒绝 / 升级；不自动发送 |
| 内容端 | 若涉及知识 / 话术，支持起草、复核、发布、暂停、下架、回退与记录 |
| 反馈 | 采用、大幅修改、拒绝、升级、未命中、问题类型和最终任务结果 |
| 权限 | 最小 RBAC；管理、复核、坐席和只读角色 |
| 可观测性 | 使用、质量、成本、错误、审计与安全事件 |
| 运行 | 监控、备份、恢复、回退、值班和支持边界 |

### 4.2 Out of Scope

- 自动点击发送、自动接管客服会话或 RPA 代回；
- 四个业务方向在一期同时开发；
- 自动作出质检处罚、合规终局判断或业务批准；
- 客服桌面客户端深度嵌入；
- 外包网络、账号、终端和权限全量开通；
- L3 复杂推送、完整多级审批和大规模版本治理；
- 供应链备案、BOM、对账、预警或相关预算；
- 将已收尾汇报 Web 直接改造成生产产品。
- 任何早期学习项目的代码、数据、配置、账号、部署或迁移。

### 4.3 Web 与供应链边界

| 对象 | 现行定位 | 可以复用 | 不可继承 |
|------|----------|----------|----------|
| `web-decision-brief` | 已收尾的汇报 Web / 设计参考 | 克制配色、信息表达、交互经验、测试方法 | 页面结构、业务状态、产品代码和技术架构 |
| 供应链 | 组合 P1、独立项目、当前暂停 | 未来可复用门禁方法和评测框架 | 客服预算、Owner、WBS、Ddev、指标或资源 |

## 5. 用户与责任

### 5.1 核心用户

- 一线坐席与班组管理者；

- 客服 BP；
- 内部试点坐席；
- 项目负责人 / FDE；
- IT、安全、运维与预算责任人。

### 5.2 责任分工（工程台账简称 RACI）

| 事项 | A（唯一） | R | C | I |
|------|-----------|---|---|---|
| 项目结果与范围 | 项目负责人 | FDE | 客服业务 Owner、IT / 安全 | 公司批准人 |
| 业务优先级、业务覆盖与验收 | 客服业务 Owner（待具名） | 业务验收人 | 试点坐席、FDE | 项目负责人 |
| 权威内容、字段、版本与发布 | 内容 / 话术 Owner（待具名） | 内容维护 / 复核人 | 客服 BP、坐席代表、FDE | 试点坐席 |
| 费用与 cap | 预算责任人（待具名） | 财务 / 采购接口人 | 项目负责人 | 公司批准人候选（待核验） |
| 数据与安全 | IT / 安全责任人（待具名） | FDE / 系统管理员 | 业务 Owner | 项目负责人 |
| 技术交付 | 项目负责人 | 前端、后端、AI、QA、运维 | 设计、数据、业务 | 公司批准人候选（待核验） |

同一事项只能有一个 A。人员 / 角色代号、代理人代号和接受职责的 `EVD-*` 证据 ID 填入 [`02-G0责任与证据台账.md`](02-G0责任与证据台账.md)。

1. [`02-G0责任与证据台账.md`](02-G0责任与证据台账.md) G0-02～G0-15 全部 Pass；

D0、会议日期、代码提交或口头“先做起来”都不能倒推出 Ddev。

## 8. 费用与止损

| 规则 | 口径 |
|------|------|
| 费用范围 | 只覆盖客服 Agent 一期已冻结主任务 |
| A 路径 | 月 cap、全期 cap、科目和预算责任人正式批准后执行 |
| B 路径 | 方向继续，保持 0 新增付费，并写下次费用决策日 |
| C 路径 | 暂停执行，记录原因、复审条件和日期 |
| 技术降级 | 关键词或更低成本方案能满足门槛时，不以“必须使用模型”为目标 |
| 止损 | G0、G1a、Pilot Ready、G1b 任一 Fail，先整改或停止，不自动扩面 |

详细模型见 [`04-费用与成本控制.md`](04-费用与成本控制.md)。

## 10. 治理与变更

- 范围、里程碑、成本或成功标准变化，先提交 CR，再更新章程；
- Owner、动作、证据、风险和决定只在 G0 台账维护；
- 评测数据、公式、阈值和签发只在 Scope 与验收文档维护；
- 周报只引用真源，不复制另一套项目状态；
- 08-04 若主任务变化，先登记 CR / DEC，再同步范围、排期、费用与评测；
- 自动代回、桌面嵌入、外包全量和供应链均视为新阶段或新项目，不得静默并入一期；
- 汇报 Web 不再拥有当前业务状态。
