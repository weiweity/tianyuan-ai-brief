# 客服 Agent · 全栈交付计划

> **给客服同事的一句话：** 项目侧建议先做“证据型客服助理 + 灰度前影子回放”，2026-08-04 请客服用真实任务确认、修正或否决
> **当前状态：** 项目已批准；一期建议为 `PRECONFIRM`；开发开工许可（Ddev）未成立；产品代码未创建
> **工程原则：** 这是全新项目，不沿用早期学习项目；汇报 Web 只参考配色与表达方法
> **版本：** v2.1 · 2026-08-03

## 1. 客服一期怎么形成闭环

```text
坐席输入问题与必要上下文
      ↓
系统做关键词 / 语义混合检索
      ↓
展示候选话术、权威原文、来源、版本、平台 / SKU / 活动有效期
      ↓
信息不足则澄清；冲突、过期或无依据则升级
      ↓
坐席核对并人工采用、修改、拒绝或转人工
      ↓
系统记录查询、候选、编辑差异与最终结果，供内容治理和评测
```

以上是项目侧推荐闭环，只有客服确认后才进入正式 Scope。系统不能自动替客服做高风险决定或发送消息；来源不可靠、权限不足、信息不足或结果不确定时，必须澄清、升级或回到人工流程。

## 2. 从启动会到灰度上线

| 阶段 | 客服团队要做什么 | 工程团队要做什么 | 通过标准 |
|------|------------------|------------------|----------|
| 启动会 | 确认、修正或否决项目侧建议，讲清真实任务、现状、成功与停止条件 | 记录系统、数据和安全限制 | 一期主任务与负责人明确或形成 OPEN 补证项 |
| 方案确认 | 提供样本、权威来源和权限 | 对比最简单可行方案，形成技术选择记录 | 范围、费用、风险可控 |
| 开发前总检查（G0） | 确认验收人和 3–5 名试点坐席 | 核对 15 项门禁与回退方案 | 全部通过并留证 |
| 开发与联调 | 参与短周期演示 | 建前端、后端、AI / 规则、数据与监控 | 核心流程端到端可用 |
| 影子回放 | 独立盲审冻结历史问题的系统结果 | 用同一内容快照对比关键词基线与候选方案 | 错误直答、过期 / 错配、越权与自动代发均为 0 |
| 内部灰度 | 真实使用并记录问题 | 监控效果、稳定性、费用和安全 | 达标继续；触线停止 |
| 验收移交 | 按约定指标签字 | 交付运行、恢复和维护说明 | 证据完整、责任明确 |

启动会不要求客服人员选择编程语言、数据库或 AI 框架。客服只需要说明业务事实和限制；工程团队在 8 月 5–6 日用小实验比较方案，并把理由写成可复核的技术选择记录（ADR）。

## 4. 一期软件边界

若客服确认推荐方案，一期只做商品 / 活动话术查询与确认的最小闭环，至少包括：

- 清楚的登录与权限；
- 唯一且可靠的数据 / 文档来源；
- 一条从自然语言查询、必要上下文、证据展示、澄清 / 升级到人工确认的完整流程；
- 来源、版本、适用平台 / SKU / 活动与有效期；
- 采用、修改、拒绝、澄清、转人工、未命中、编辑差异和最终结果记录；
- 灰度开关、监控、备份与快速退回原流程；
- 3–5 名试点坐席可完成真实任务。

一期不做：自动代发、订单 / 物流 / 退款 / 售后系统深度集成、所有平台一次接入、供应链需求、对外大规模上线或自治 Agent。

## 5. 技术选择顺序

工程团队按以下顺序做决定：

1. 一期到底解决哪一个真实任务；
2. 用户是谁、在哪个平台工作、预计多少人使用；
3. 正确答案来自哪里、谁能修改、谁能批准；
4. 哪些数据敏感，是否允许进入 AI 模型；
5. 不用 AI 的最简单方案能做到什么程度；
6. AI 能否带来可测的额外价值；
7. 如何记录、监控、备份、恢复和停止；
8. 最后再选择前端、后端、数据和 AI 技术。

技术栈结论由工程负责人提出，由 IT / 安全和项目负责人复核；不会让客服人员在会上对技术框架投票。

项目侧建议“证据型客服助理”不等于已经选定大模型、向量数据库或 RAG 框架。工程仍须用关键词 / 规则基线与语义方案做小实验；无可解释增益时选择成本更低、风险更小的实现。

## 6. 开发与发布流程

```text
任务可开发
   ↓
设计、接口、数据、测试共同评审
   ↓
小步开发并自动测试
   ↓
测试环境验证
   ↓
客服验收
   ↓
冻结历史问题影子回放与业务盲审
   ↓
3–5 名坐席内部灰度
   ↓
达标继续 / 触线停止并回退
```

### 环境

| 环境 | 使用什么数据 | 用途 |
|------|--------------|------|
| 本地 | 生成或脱敏样本 | 开发和基础测试 |
| 测试 | 冻结的脱敏数据 | 联调、完整测试和安全检查 |
| 影子 | 冻结的脱敏历史问题与内容快照 | 业务盲审，不向真实客户展示 |
| 灰度 | 批准的最小真实数据 | 3–5 名内部坐席试用 |
| 正式环境 | 一期默认不扩面 | 灰度验收后另行批准 |

## 7. 上线前必须验证

| 类别 | 通俗检查 |
|------|----------|
| 业务 | 真实任务能否完整完成，结果是否比原流程更好 |
| 权限 | 不该看的人是否看不到，不该改的人是否改不了 |
| 数据 | 来源、版本、过期、重复和敏感内容是否受控 |
| AI / 规则 | 普通情况、难题和必须转人工的情况都经过测试 |
| 性能 | 预计人数同时使用时是否稳定，慢时是否能降级 |
| 兼容 | 客服实际电脑、浏览器、分辨率和网络是否可用 |
| 运行 | 出问题能否告警、恢复、回退并找到负责人 |
| 费用 | 单次、每日和每月费用是否可见，超线是否能停 |

不能只展示成功案例；失败样本、边界情况和回退步骤必须一起验收。

## 8. 三阶段工程路线

| 阶段 | 工程重点 | 明确边界 |
|------|----------|----------|
| 一期 | 商品 / 活动话术证据检索、内容治理、影子回放、3～5 人内部灰度、完整埋点与人工确认 | 不自动发送，不做正式规模收益和显著性主张 |
| 二期 | 扩大测试覆盖、数据清洗、语料蒸馏、稳定性与缺陷收敛；支持同期分层 A/B | 不从一期自动扩面，预算、安全和范围重新批准 |
| 三期 | 在已验证内容、评测和运行底座上建设客服 Agent | 自主程度、发送权限和责任边界另行立项 |

## 9. 什么任务可以进入开发

每项开发任务必须先有：用户与问题、做与不做、验收条件、界面状态、数据与权限影响、测试方法、负责人、依赖和回退办法。关键内容缺失时保持“未准备好”。

## 10. 什么才算完成

只有在代码和文档经过复核、自动测试通过、权限和异常状态完整、数据记录可观察、没有未处理的严重风险、业务验收证据归档、回退可执行时，功能才算完成。

“页面能打开”或“AI 回答了几个问题”都不等于完成。

## 11. 给工程同事的附录：建议代码结构

开发开工许可（Ddev）成立后，再新建独立产品目录：

```text
customer-service-agent/
├── apps/
│   ├── web/                 # 客服与管理页面
│   └── api/                 # 数据、权限、反馈与审计接口
├── packages/
│   ├── contracts/           # 前后端共同约定
│   ├── intelligence/        # 规则、检索或 AI 能力
│   └── evals/               # 可重复运行的效果评测
├── infra/                   # 环境、监控、备份与恢复
├── tests/                   # 功能、接口、安全、性能和端到端测试
├── scripts/
└── docs/                    # 技术选择、运行手册和接口说明
```

该目录是新项目边界；不会审计、迁移或依赖早期学习项目。已收尾汇报 Web 只可参考克制的紫色配色、信息层级、响应式和可访问性方法，不继承其业务内容、状态、预算或代码结构。
