## 2. 60 分钟会议怎么开

> **唯一议程真源：** [`02-G0责任与证据台账.md` 第 4 节](02-G0责任与证据台账.md#4-8-月-4-日启动会议程)。本表是客服主持版镜像，时间、议题和结论必须逐项一致；生成与测试会在漂移时失败关闭。

| 时间 | 讲什么 | 必须得到的结果 |
|------|--------|----------------|
| 0～5 | 边界与分工 | 项目已批准；今天只处理一期业务问题与后续责任；不选技术栈、不宣布开工 |
| 5～15 | 看真实任务 | 至少 2 个脱敏真实任务：谁、在哪个平台、怎样处理、耗时 / 错误 / 升级证据 |
| 15～23 | 选一期主问题 | 一个主问题 + 为什么不先做其他方向；证据不足则 OPEN |
| 23～30 | 定一期边界 | 主用户、主场景、最小闭环、人工确认、In / Out |
| 30～38 | 定成功与停止 | 成功 / 停止指标只定名称、来源与 Owner；无基线不填目标值 |
| 38～45 | 定真源与责任 | 权威来源、权限、内容 Owner、冲突裁决；缺项写 Owner 和补齐日期 |
| 45～52 | 定试点与规模 | 3–5 名试点分层原则、预计总人数 / 峰值；技术限制转 ADR 清单 |
| 52～60 | 回读决定与未决 | DEC-REQ-01～09 逐项标记 DEC / PRECONFIRM / OPEN / PARKING，并写 Owner、截止日、证据位置 |

主持规则：

- 会前具名：主持人（项目负责人）、最终业务拍板人（客服业务 Owner 候选或客服总监，二选一）、计时人（客服经理）、记录人（客服 BP）、工程答疑人（FDE）。
- 先讲真实工作，再谈功能；禁止从“AI 能做什么”倒推需求。
- 四个候选方向——知识 / 话术辅助、智能质检、反馈分析、聊天分析——只是讨论起点，不是预设答案。
- 不按举手或票数决定一期方向。客服负责人根据真实频次、业务影响、数据条件和两周可验证性做决定，并记录理由。
- 不让客服人员选择编程语言、数据库或 AI 框架；客服只确认业务事实、限制和验收标准。
- 每段结束前 2 分钟提醒，到点硬切；单人陈述不超过 60 秒，反对意见不超过 30 秒。
- 最后 8 分钟不得挪用。技术栈、API 实现、容量阈值、费用数字、供应链和超时讨论进入 `PARKING`。
- 只用四种状态：`DEC（已决定）`、`PRECONFIRM（会前已填、现场待确认）`、`OPEN（待补证）`、`PARKING（不在本会决定）`；后三种必须写负责人和日期。

## 3. 会议必须处理的 9 件事

| 决策 ID | 60 分钟内要做到 | 合格答案长什么样 |
|---|---|---|
| DEC-REQ-01 · 一期主问题 | 条件决定 | 有真实任务和损失证据就决定；否则 `OPEN + 补证人 + 日期` |
| DEC-REQ-02 · 主用户与场景 | 条件决定 | 具体到哪类坐席、哪个工作平台和哪个任务，不填真实姓名 |
| DEC-REQ-03 · 最小闭环 | 决定业务边界 | 一条最小业务流程与人工对照；技术实现会后由工程验证并书面记录 |
| DEC-REQ-04 · 做什么 / 不做什么 | 现场决定 | 自动代发、四方向并行、供应链等明确排除项 |
| DEC-REQ-05 · 成功 / 停止 | 决定指标名称、来源、Owner | 没有基线不编目标值；公式与阈值最迟 08-12 由业务与 QA 共同确认 |
| DEC-REQ-06 · 权威来源 | 会前预填、现场确认 | 候选可靠来源、内容 Owner 与冲突裁决；权限细节会后补齐 |
| DEC-REQ-07 · 试点人口 | 决定选择原则 | 3–5 名试点的分层、替补和退出；名单受控签发 |
| DEC-REQ-08 · 系统约束 | 只收业务输入 | 总人数、峰值、平台、设备和网络；技术方案和容量由工程会后验证并书面记录 |
| DEC-REQ-09 · 后续责任 | 现场决定 | 项目、业务、内容、验收和工程各有唯一拍板人 / 执行人、截止日和证据位置 |

### 会中直接使用的提问

1. 客服每天最频繁、最耗时或最容易出错的真实任务是什么？
2. 这个问题一周发生多少次，影响哪些人，有哪些脱敏案例？
3. 现在怎样处理，用多久，常在哪一步返工或升级？
4. 哪份文档或哪个系统才是正确答案，冲突时听谁的？
5. 软件给出帮助后，坐席必须怎样核对和人工确认？
6. 哪个数字改善才算有效，数据从哪里取、由谁解释？
7. 出现什么错误、风险、费用或稳定性问题必须立即停？
8. 先由哪 3–5 名坐席试用，他们用什么电脑、浏览器和网络？
9. 后续预计多少人同时使用，是否有高峰时段？

## 4. 会议结束的判定

以下内容齐全，会议才算成功；成功不要求九项全部为 `DEC`：

- DEC-REQ-01～09 都有 `DEC / PRECONFIRM / OPEN / PARKING` 状态之一；
- 每个非 `DEC` 项都有原因、唯一负责人、截止日和完成证据位置；
- 主问题、主用户和 In / Out 有证据则决定，无证据则明确补证；
- 指标、真源、试点和系统限制至少确定口径、负责人和下一拍板时间；
- 所有人理解“需求会完成”不等于“开发开工许可（Ddev）成立”；
- 会后 2 小时内发送纪要，异议和未决项不得被省略。

若一期主问题或成功标准仍不明确，允许继续补证，不为赶进度假装形成结论。

## 7. 每周更新顺序

1. 责任与证据台账：人、动作、证据、风险和决定；
2. Scope 与验收：范围、指标、数据和停止条件；
3. 项目章程：目标和里程碑；
4. 总排期：日期、资源和顺延；
5. 项目驾驶舱：整体状态和下一关；
6. 周报：只摘录以上真源，不自行改口径。

## 8. 升级规则

| 情况 | 处理 |
|------|------|
| 关键负责人逾期 | 当日升级给项目负责人和客服负责人 |
| 一期问题、范围或指标变更 | 记录变更理由，重新评估日期、费用和测试 |
| 数据来源冲突 | 暂停使用，先由内容 / 数据负责人确认唯一真源 |
| 严重安全或隐私问题 | 停止开发、发布或灰度，完成修复与复测 |
| 错误、稳定性或费用触线 | 关闭灰度开关，退回原流程并启动复盘 |
| 供应链事项进入客服资源 | 移回供应链独立项目，不占客服一期资源 |
| 汇报 Web 被当作当前系统 | 立即纠正：它已收尾，只是设计与表达参考 |
