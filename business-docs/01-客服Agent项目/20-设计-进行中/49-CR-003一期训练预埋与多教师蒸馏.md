## 0. 结论

一期需要为三期客服 Agent 留下可用的数据地基，但不能把短期运行日志直接变成训练集。冻结方案是：

1. 一期线上仍用 Unicode bigram；训练侧只创建合同、空模板与纯合成 fixture，纯合成本地影子只验证结构，不生成真实 embedding / teacher / student 制品；
2. 自动事实只形成**候选证据**，不自动形成正确标签；
3. raw 原句 / 脱敏问法 / 个人事件的 `0 / 14 / 30` **均为建议值，待 G0-11**；只有获批语义资产可以走独立保留期；
4. 问法语义资产与 Answer 发布资产解耦，但每个训练样本必须绑定 `release_id + script_id + script_version + content_hash`；
5. 二期须另行取得范围、数据、安全、费用与训练授权后，才可只训练检索、意图、重排；两周一个不可变版本，人工审核、人工发布；
6. DeepSeek 仅为可替换教师候选，GLM 无书面授权禁止蒸馏；教师运行不可变、抗注入、隔离且受预算 cap；
7. `train / G1a / G1b` 按语义簇、来源与模板祖先隔离，禁止评测污染；
8. 三期客服 Agent、生成回复或自动回复另立项，不从一期预埋或二期训练自动继承授权。

这是一条“可审计、可删除、可替换”的训练预埋链，不是一期训练授权。

## 2. 分层架构

```text
在线运行面（一期）
  Unicode bigram → Top3 → 自动事实账
       │                         │
       │                         └─ 行为只产生候选，不是标签
       ▼
短期数据层
  raw 0 天（建议/待 G0-11） ──DLP──► 脱敏问法 14 天（建议/待 G0-11）
                                             └────► 个人结构事件 30 天（建议/待 G0-11）
                                      │
                                      ▼
语义资产晋级门（非自动）
  二次 DLP → 语义归并 → 业务审 → 数据安全审 → 用途锁定 → 删除血缘
                                      │
                                      ▼
隔离训练面（二期另批）
  dataset manifest → train/validation → embedding shadow / teacher → student
                                      │
                                      ▼
人工发布门
  离线评测 → G1a/G1b 隔离核验 → 双审 → 人工发布 / 回滚
                                      │
                                      ▼
客服 Agent 面（三期另立项）
  生成回复 / 自动回复 / Agent 能力须单独范围、安全、费用与上线授权
```

### 2.1 `0 / 14 / 30` 与语义资产不是同一保留账

| 层 | 建议保留 | 内容 | 到期动作 |
|----|----------|------|----------|
| raw | **0 天（建议，待 G0-11）** | 未脱敏搜索原句 | 请求结束即释放；不得进入日志、trace、缓存或 fixture |
| redacted text | **14 天（建议，待 G0-11）** | 获批字段的脱敏问法正文 | 删除正文、派生索引与缓存；保留许可的聚合计数 |
| personal event | **30 天（建议，待 G0-11）** | 用户代号、候选、复制 / 放弃 / 升级 / 重选结构事件 | 删除或不可逆聚合；不得继续支撑个人明细 |
| promoted semantic asset | **独立建议，待 G0-11 与资产晋级门批准** | 去身份、去时效噪声、经双审的语义表达与标签 | 按资产策略删除，并沿血缘传播到数据集、向量、teacher-run 引用和恢复副本 |

`0/14/30` 当前均是提交 G0-11 的建议，不是已授权值。数据在建议期限内存在，不代表可训练；晋级后也不能因为“已脱敏、已向量化、已蒸馏”而拒绝删除请求。

## 3. 语义资产晋级门

### 3.1 输入候选

候选可来自人工 Question、批准的 policy 样本、纯合成样本或 CR-002 自动事实。自动事实候选至少包含：

- `query_id / parent_query_id / attempt_kind`；
- `semantic_family_id` 候选与来源集合哈希；
- 脱敏问法或 `suppressed` 状态；
- 候选 `release_id + script_id + script_version + content_hash`；
- 复制 / 无命中 / 放弃 / 升级 / 重选事实；
- 三维离线复核的修改、发送、适用性结论（可分别 `unverifiable`）。

行为信号只能进入“待审候选池”。复制最多说明候选被复制，不能自动标成相关、正确、已发送或优质答案。

### 3.2 晋级步骤

| 步骤 | 必要证据 | 失败动作 |
|------|----------|----------|
| P1 来源与告知 | collection mode、告知版本、权限、来源许可 | 拒绝晋级 |
| P2 二次 DLP | PII、订单、店铺、活动时效与可逆标识扫描 | 删除 / 重脱敏，不进入下一步 |
| P3 语义归并 | `semantic_family_id`、精确 hash、近重复、模板祖先 | 合并或拒绝，禁止跨 split 泄漏 |
| P4 业务审核 | 意图、问法自然度、答案绑定与适用窗口 | `candidate` 保留或拒绝 |
| P5 数据安全审核 | 用途、保留、出域、许可、删除路径 | 未批准即 fail-closed |
| P6 用途锁定 | 只选 retrieval / intent / reranker 之一 | 用途变化新建 CR / 新版本 |
| P7 manifest | 数据集版本、cutoff、hash、分账、审批、删除血缘 | 缺字段不得发布数据集 |

业务审批和数据安全审批必须是两个独立 capability 的明确记录；同一 FDE 可以承担多个工作角色，但不能用一次点击替代两种审查口径。

## 4. 问法与答案解耦

Question 资产表达“用户可能怎样问”，Answer 发布资产表达“此刻允许怎样答”。两者不能共用生命周期：

- Question 使用稳定 `semantic_asset_id / semantic_family_id`；
- Answer 使用内容发布链和有效窗口；
- 每个样本只保存发布绑定 `release_id + script_id + script_version + content_hash`，不得只保存 `script_id` 后回读当前正文；
- Answer 下架、回滚或过期后，旧绑定立即不可推荐；Question 是否继续保留由独立用途、许可和删除策略决定；
- 若同一问法在不同平台 / SKU / 活动期指向不同答案，必须拆分 policy 条件，不能把冲突答案压成一个标签。

## 5. 数据集、隔离与版本

### 5.1 数据账

| `data_account` | 含义 | 当前允许 |
|----------------|------|----------|
| `synthetic` | 全部主体、问法、ID 与答案均为虚构；用于 schema / 管线测试 | **是** |
| `policy` | 由批准政策或话术规则人工构造，不声称来自真实行为 | 仅在批准范围内 |
| `real` | 来自真实运行或真实业务文件，即使已脱敏 | **当前为 0；NO-GO** |

三账不得相互抵消。报告必须分别给出样本数、拒绝数、授权、成本、失败与产物 hash。

### 5.2 切分门

- artifact 内只允许 `train / validation`；G1a/G1b 保持独立评测 manifest，不进入训练 artifact；
- 在切分前以 `semantic_family_id`、精确指纹、近重复指纹、lineage group 和 template ancestor 去重；
- `train ∩ G1a = train ∩ G1b = G1a ∩ G1b = 0`，交集按全部上述维度计算；
- teacher prompt、embedding 索引、阈值调参和错误分析样本都视为“见过”，不得再进入 G1a/G1b；
- 评测结束后要吸收入训，必须新建未来数据集与未来评测窗口，不回写旧结果。

### 5.3 双周版本

二期另批后，每两周最多形成一个 `dataset_version` 和对应 `model_version`。冻结内容包括 cutoff、schema、样本 manifest、分账、审批、teacher runs、训练参数、模型 / tokenizer / license hash、离线指标和回滚目标。训练或评审失败可不发布，但不得覆盖旧版本；线上发布只允许人工批准的不可变制品。

## 6. Embedding、教师与 student

### 6.1 一期纯合成影子合同

- 在线：Unicode bigram 是唯一验收主路；
- 离线合同：默认后端候选为本地、许可已审的小型开源 embedding；
- 输入：**一期仅纯合成 fixture**，不接“另行批准的真实集合”捷径；真实数据影子归入二期另批训练门；
- 输出：只允许纯合成结构 / 召回测试结果，不形成可发布模型，不影响线上返回、G1a 判定或自动晋级。

### 6.2 教师策略

| provider | 地位 | 启用门 |
|----------|------|--------|
| local policy / rule | 合成 fixture 默认 | 无外发；仍须严格 schema 与审计 |
| DeepSeek | 可替换教师候选 | 具体模型 / 版本、条款、采购、地域、保留、蒸馏用途、数据字段与 cap 全部书面批准 |
| GLM | 默认禁止 | 只有明确写明“允许蒸馏”的书面授权才可建立 run |
| 其他教师 | 非默认 | 新 provider 审查，不得借兼容接口自动启用 |

教师不是权威来源。输入中的客户话术、HTML、Markdown、JSON 字符串和指令片段均视为不可信数据：系统指令与数据分通道；字段、长度、深度、字符集白名单；输出只接收 `additionalProperties=false` 的 JSON；尾随文本、角色越权、工具调用、链接取数和提示注入全部拒绝。

### 6.3 student 与隔离

student 只选择许可兼容、来源可验证的小型开源模型；保存模型卡、许可证文本 / ID、权重来源和 hash。训练环境无生产数据库写权限、无外网默认访问、无生产密钥；数据通过只读版本制品导入，输出进入隔离 registry，必须人工发布。

### 6.4 不可变 teacher-run 与费用

每次 run 必填：`run_id`、provider / model / version、许可与授权 ID、prompt / config hash、input dataset hash、output hash、参数 hash、开始 / 结束时间、操作者、token、实际费用、币种、单次 / 批次 / 月 cap、抗注入结果与审查结论。run 只追加；重跑生成新 ID，不能覆盖。

费用路径 B、G0 或 Ddev 未成立时，外部教师实际调用次数与费用必须为 0。任何 cap 缺失或超限都 fail-closed，不能用不完整输出冒充完整批次。

## 7. 删除血缘

最小血缘：

```text
source event / policy / synthetic fixture
  → promoted semantic asset
  → dataset version + item
  → embedding index version / teacher run
  → student checkpoint / release candidate
```

每层保存上游 ID/hash、用途、审批、保留期和下游引用。删除请求到达时：停止新使用 → 标记受影响制品 → 删除可删除正文 / 向量 / 临时文件 → 使相关未发布数据集或 checkpoint 失效 → 对不可变 run 保留最小审计 hash 而删除受保护正文 → 备份恢复后按 re-delete 清单再次删除。删除完成须可核验，不能只在主表置状态。

## 8. RBAC 与规模演进

沿用 `agent / coach / owner`，训练相关能力是叠加 capability：

| capability | agent | coach | owner | 数据安全 |
|------------|:-----:|:-----:|:-----:|:--------:|
| 查看自己的自动事实状态 | 是 | 按团队聚合 | 聚合 | 审计 |
| 查看受控脱敏样本 | 否 | 最小授权 | 最小授权 | 审批 / 审计 |
| 业务语义审核 | 否 | 可授权 | 可授权 | 只读结论 |
| 数据安全审核 / 出域批准 | 否 | 否 | 不自动拥有 | 必须 |
| 构建数据集 / 执行训练 | 否 | 否 | 需独立 capability | 需已批准 manifest |
| 发布模型 | 否 | 否 | 人工双人门 | 审批可见 |

4 人 Pilot 候选期使用单批离线复核、单 worker、人工清单即可；扩到 50–100 人时增加队列、分区 / 批处理、增量去重、审查 SLA 和成本配额，但不改变 SoR、双审、双账、用途锁定与人工发布。容量扩展不构成数据用途扩张。
