怎么看这张图（一期功能地图）

先当一张「一期到底做哪些功能」的施工图来读。上面是三种人，中间是电脑上的两个界面，下面是服务器上已经冻结的九个端口和数据库。它不发明新端口，只把功能贴到现有架构上。

图的逻辑（一句话）

一期做证据型客服助理：坐席在浮窗搜话术、核对后自己复制发送；教练/负责人在 Dashboard 看效果、管发布、做工单分析。系统不替坐席发消息，也不写回班牛。

图上有哪些「箱子」

  • 浮窗：一线主入口。粘贴问法 → Top3 已发布原文 → 复制剪贴板；有占位符只在本机内存填写；没依据就澄清或升级。
  • Dashboard：概览、检索复制流水、离线三维复核、工单分析、话术优化待办、内容发布、公告租约。
  • 九端口：auth / search / events / workorders / content+announce / metrics / policy / redaction。功能复用这些入口，不另建平行平台。
  • PostgreSQL：权威库。业务工单 work_order_* 和内部待办 iteration_task* 必须分域。
  • 紫框：训练只预埋合同和合成夹具，一期不真训、不调教师、不发模型。
  • 红框：明确不做——自动代发、读聊天、班牛写回、完整 Agent、移动端。

两条必须打通的闭环

闭环路径小白解释
话术推荐问法 → search → Top3 → 复制 → events坐席找得到可核对的话术，系统记下搜了什么、复制了哪条。
工单分析批准文件 → workorders → 聚合下钻 → 脱敏导出只分析导出文件，不自动填单、不写回班牛。

每条线是什么意思

从 → 到线型小白解释
坐席 → 浮窗；话术师/负责人 → Dashboard同步人在界面上点、粘贴、查看，马上有反馈。
浮窗 → search / events / auth同步检索、记自动事实、登录都走中心 API。
Dashboard → metrics同步读取工具指标、检索复制流水和话术优化待办。
Dashboard → events同步仅提交话术优化待办的状态变更；复制/升级事实由浮窗写入。
Dashboard → workorders / content / announce同步导入工单、发布话术、同步公告，都走现有端口。
端口 → PostgreSQL / 对象存储同步正式数据和导入原稿落权威库，不把本机缓存当真相。
坐席 → 千牛/抖音异步/人工复制后自己去接待软件粘贴发送；系统不代发、不读正文。
班牛文件 → Dashboard异步/人工人导出并批准后再导入；没有实时 API 写回。
库 → 训练预埋后置只保留以后能训练的合同和夹具，一期不启动训练。

看完记住

  1. 一期 = 浮窗搜话术 + Dashboard 治理/分析，不是自动客服机器人。
  2. 系统给候选，坐席确认后自己发；自动代发次数必须为 0。
  3. 工单分析与话术优化待办是两套东西，不能混称「工单」。
  4. 这张图是功能地图；端口细节、时序和关卡看后面 2～8 图。

怎么看这张图（给完全没看过架构的人）

先把整张图想成一张「谁和谁说话」的地图。上面是人，中间是我们做的软件，旁边是公司里/外面已经存在的系统。箭头表示「有数据或操作从 A 到 B」。

图的逻辑（一句话）

坐席/话术师/负责人通过电脑上的「壳」软件，调用公司中心的 API，API 再读写 PostgreSQL 数据库。系统能确认“脱敏后搜了什么、展示了哪个发布版本、哪条复制成功，以及显式放弃、无命中退出、超时或升级动作”；它不读取千牛/飞鸽聊天正文。是否修改、是否发送和所选话术是否适用，只进入独立的离线抽样复核，不能冒充平台核验。

图上有哪些「角色/箱子」

  • 坐席 / 话术师 / 负责人：真实的人。坐席接待客户，话术师管话术内容，负责人管发布和指标。
  • Electron 壳：装在电脑上的桌面程序，里面有浮窗和 Dashboard 两个界面。浮窗完成搜索、候选展示、复制，以及产品内可观测的显式放弃、无命中退出、超时或升级；不强制坐席回填后续使用结果。
  • Application API：跑在服务器上的中心程序，统一处理查询、发布、日志等。
  • PostgreSQL：权威数据库。全公司「正式生效」的话术和日志以这里为准。
  • 飞书 / 千牛抖音 / DeepSeek：外部系统。生产登录必须走飞书 OAuth；千牛抖音只是人工接待现场，系统不读聊天正文；DeepSeek 仅可选排序，不能改话术原文。

每条线是什么意思

从 → 到线型小白解释
坐席 / 话术师 / 负责人 → Electron 壳同步人在软件界面上点、粘贴、查看。马上有界面反馈，所以是同步。
Electron 壳 → Application API同步桌面程序通过 HTTPS 调服务器接口：搜索、候选曝光、复制终态和产品内升级动作复用现有 /v1 端口。
API → PostgreSQL同步服务器用 SQL 读/写权威话术和自动事实流水；离线抽样复核另存受控证据，不混入在线事实账。
API → 飞书（实线）同步/Must生产会话必须走飞书 OAuth；只有 development/test 可用 mock，生产不得降级成 mock。
话术师 → 飞书（虚线）异步/可选话术师可以在飞书表格里改内容，但那只是「编辑草稿台」。真正对全员生效，必须再走系统里的「发布」。
坐席 → 千牛/抖音（虚线）异步/可选坐席把推荐话术复制后，自己粘贴、可能修改并发送。系统不自动发送、不读取正文，也不自动判断是否修改、发送或答对；这些只按获批样本离线复核。
API → DeepSeek（虚线）异步/可选可选：让模型帮排序。有超时就降级为普通搜索。绝不允许模型改写话术正文。

看完这张图你要记住的 4 件事

  1. 权威话术在 PostgreSQL 的已发布快照里；每次发布还必须绑定四类已批准来源版本，飞书表或任意非空 source_ref 都不能「直接生效」。
  2. 脱敏搜索原句 + 绑定版本候选 + 复制 / 退出 / 升级是产品内自动事实，不是完整聊天记录；复制不等于发送，离线抽样结论也不等于平台原生核验。
  3. 实线是必须走通的主路径；虚线是可选或外部协作。
  4. 演示成不成功，不能用来裁剪这张边界图。

怎么看这张图（小白版）

这张图把「中间的软件」拆成可安装、可扩容的几大块：左边是坐席电脑上的程序，中间是服务器上的 9 个功能入口（端口），右边是数据库和文件，最边上是可选的 AI/后台任务。箭头表示调用关系。

图的逻辑（一句话）

界面只负责展示和操作；所有业务规则走 API 的各个端口；只有 content 端口能做「正式发布」；search/events/content 是红线，改坏了会影响全员。

图上分区是什么

  • 客户端层：Float 浮窗给一线用；Dashboard 给话术师/管理用；IPC 是壳内部的安全通道；可选 SQLite 只是本地缓存，不是权威库。
  • API 层 9 个端口：每个端口干一类事（登录、搜索、日志、指标、工单分析、发布、公告、策略开关、脱敏）。CR-002 复用 search/events/metrics，不另建第十个平台。
  • 数据层：PostgreSQL 存正式数据；对象存储放上传的 Excel 原稿文件。
  • 异步与可选旁路：一期导入必须经过持久 outbox + TypeScript Import Worker；可选的只有 LLM 排序、本地缓存和二期 Python 清洗。

每条线是什么意思

从 → 到线型小白解释
Float/Dashboard → Preload IPC同步界面点按钮后，先经过壳内白名单通道，不能随便访问系统。
IPC → auth同步问服务器：我是谁、什么角色（坐席/话术师/负责人）。
IPC → search（红线）同步提交客户原话，立刻要返回最多 3 条推荐话术。这是一线最高频路径。
IPC → events（红线）同步记录绑定发布版本的候选、复制成功、显式放弃、无命中退出、客户端生命周期超时与产品内升级；不保存最终发送正文。
IPC → metrics同步Dashboard 按根问题账和搜索操作账展示工具侧复制、无命中、放弃、超时和升级；离线三维抽样单独报告，不写成总体采纳率或经营大盘。
IPC → content（红线）同步导入 Excel、点发布。服务端先核对四域来源版本；任一未批准、暂停、域错或 hash 错则整单拒绝。
IPC → announce同步客户端问：有没有新版本话术库？有就分页下载快照并确认收到。
search → redaction同步写日志前先脱敏（如手机号打码），保护隐私。
search / events / content / announce → PostgreSQL同步真正读权威话术、写流水、发布事务、读公告快照，都进数据库。
content → 对象存储同步上传的原始 Excel/CSV 文件落盘保存，方便核对「当初导了什么」。
search → LLM（虚线）异步/可选可选重排序。超时就退回普通搜索，不能让坐席一直转圈或改话术字。
content → outbox（异步边界）异步/Must上传落持久存储后，API 在同一数据库事务写 batch + outbox，成功后才返回 202 validating。
outbox → TypeScript Import Worker（虚线）异步/Must一期后台工人用 claim/heartbeat/fencing 校验导入并原子落 staging；Python 清洗才是二期。
announce → 本地 SQLite 缓存（虚线）异步/可选下载新话术后，电脑可在本地重建搜索索引；但它不是权威库，短时 lease 过期且离线时必须停止检索，避免继续用已暂停来源。

看完记住

  1. 红线端口 search / events / content 改动要特别小心。
  2. LLM 等可选旁路挂了，检索仍要能用；导入 Worker 挂了则明确积压/告警，不能假成功。
  3. 本地缓存永远不能冒充「全公司正式话术库」；来源 lease 失效时不能继续离线返回。

怎么看这张图（小白版）

这是「按时间顺序发生了什么」的图，从上到下读。上面一块是「话术师导入/修正，负责人发布新话术」；下面一块是「坐席查询并复制话术」。每条横线是一次请求或返回。

图的逻辑（一句话）

先发布成功，全员才能查到新话术；坐席查询时答案必须来自已发布版本；复制成功才写入兼容名为 adopted 的事件，它只代表复制，不代表发送、实际采纳或正确。

上半部分：发布管线（按步骤）

  1. 话术师上传表格并选择服务端已批准的来源版本 → 系统核对域、hash 与暂停状态后进「暂存」，还没对全员生效。
  2. 负责人确认并点发布（话术师只预览/修正）→ 服务器先核对合并后的完整快照必须绑定售前、活动、售后、产品四类来源，再加锁做一次事务：更新正式库、冻结合照、换「当前版本号」、写公告和审计。
  3. 坐席电脑发现版本新了 → 分页把快照与来源 binding hash 拉完 → 本地可选重建索引 → 告诉服务器「我收到了」；lease 过期且离线就停用。

下半部分：检索、复制与自动事实（按步骤）

  1. 坐席粘贴客户原话 → 调 search。
  2. 服务器限流、写查询日志、只读「当前发布快照」里的话术，并过滤过期内容。
  3. 可选：问 DeepSeek 帮排序；超时就不用它。
  4. 返回最多 3 条原文 → 坐席点选 → 复制到剪贴板。
  5. 只有复制（或受控的实验性自动填）成功，才写入 adopted 兼容事件；UI 和报表统一叫「复制」。
  6. 系统自动记录脱敏搜索原句、候选话术、复制成功、无命中/放弃/升级和客户端生命周期超时；修改程度、是否发送和话术适用性只在获批样本中做离线三维抽样，不要求坐席强制回填。

每条线是什么意思

步骤线线型小白解释
上传 → import同步提交服务端先解析已批准 source_version_id；文件持久化且 batch+source bindings+outbox 提交后才返回 202「校验中」。
import → 数据库写 staging同步暂存数据落库，但搜索还搜不到这些新行。
发布 → publish同步带幂等键；服务器用非阻塞锁保证同一时间只有一个发布。
publish 事务写库同步合并后四域来源和全部话术要么整包成功，要么整包失败；不允许旧来源残留与新来源混成半套快照。
客户端 current / snapshot / ack同步问版本、分页下载、确认收到，都是请求-响应。
本地重建 FTS异步/本地在自己电脑上建索引，不占用发布事务时间。
search 主路径同步坐席需要马上看到 Top 结果；服务端只能调用受控 search_recommendable_scripts，不允许 runtime 直读底表或视图绕过治理门。
search → DeepSeek异步/可选可跳过；超时必须降级，不能卡死。
adoption 写库同步记录是否真的复制成功；兼容字段 adopted 只表示复制，不代表发送或答对。
离线三维抽样离线/受控按获批样本分别复核修改程度、是否发送和话术适用性；不设在线结果回填入口，不把复制推断为发送或正确。

看完记住

  1. 没点发布，或四域来源有一项不合格 = 全员搜不到你刚改的表。
  2. 答案永远是库里的原文，不是 AI 现编的。
  3. 在线自动事实与离线修改 / 发送 / 适用性三维样本分账；正确性只靠授权抽样复核。
