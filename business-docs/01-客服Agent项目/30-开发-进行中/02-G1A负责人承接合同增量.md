## 1. 承接范围与不变量

- 只针对实际批准的、明确版本的四域来源及精确条目集合；未来版本、增加/删去条目、正文/Question/范围/有效期/风险字段变化不能继承旧承接记录。
- 使用独立 `owner_acceptance` 模式，一名负责人真实承担内容批准责任；不伪装成 `dual`，也不填写虚假的 secondary reviewer。
- 不重写业务原文，不按域硬编码风险，不清空风险类别求通过。延续 high 对应非空风险类别、low/medium 对应空类别的现行机器约束。
- 仍存在冲突的条目不能用承接自动清除冲突；本合同明确要求 `has_conflict=false`。冲突需先真实处理再形成新版本。
- 负责人承接不是 QA、DLP、独立盲审、T6、上线或生产授权。新记录没有延长现有来源、内容或评测包有效期的能力。
- 实际记录、来源摘要、主体 hash 与批准证据仅存仓外受控空间。仓内仅保存 schema、校验器、纯合成测试和本说明，不生成真实批准记录。

## 2. 已有能力与方案比较

产品 `apps/api/tests/support/g1a-e0/input-package.ts:409–416` 强制 high/冲突走 dual；治理 `33-schema-v1-草案.sql` 的 scripts、staging_scripts、release_items 均有对应约束。`content_governance_snapshot/hash` 还绑定审核字段，产品 loader 在写入前重验 hash；单改 JS 无法解除数据库拒绝。

采用受限、版本绑定的承接记录，并复用当前四域 source gate、内容 hash、独立 manifest 锚点、不可变 migration 控制面及 SearchBackend。不新增审核服务、不新增数据库连接池、不重写检索器。

不采用全局“单人模式”开关：它会使未知或未来内容继承本批决定。不采用把同一人伪装成双审或删除数据库约束：前者伪造事实，后者留下绕过装包器直写的缺口。

## 3. 机器记录与信任来源

机器 schema：[owner-acceptance.v1.schema.json](owner-acceptance.v1.schema.json)。验证入口：`sites/scripts/customer-agent-owner-acceptance.mjs` 的 `verifyOwnerAcceptance(rawRecord, options)`；这是治理验证工具，不是产品 runtime。

记录包含 schema、用途 `g1a_offline_only`、模式 `owner_acceptance`、负责人伪名 hash、批准 EVD、接受/到期时间和精确 scope。scope 只包含四个来源版本/快照摘要/复核截止日期，以及条目身份、版本、来源、风险状态与 `review_input_sha256`，不含原文。

记录使用递归 ASCII 键排序、JSON 标准标量编码、原数组顺序、无缩进、末尾单个 LF 的 UTF-8 字节。所有键由闭合 schema 固定。来源按 domain、条目按 script_id、风险类别按字符串升序排列并去重后交给批准流程；校验器不排序修复输入。重复 JSON 键、CRLF、不同数字表示、额外字段及超 2 MiB 记录拒绝；条目上限 5,000 是验证资源上限，不是新增业务授权。

`options` 的三个信任输入必须由受控执行器提供：

1. `approvedRecordSha256`：在包外核验真实批准记录后取得的精确字节 SHA-256，不能从候选包自己计算后自证。
2. `expectedOwnerSubjectHash`：同一真实批准证据确认的负责人，不接受候选文件自报身份。
3. `now`：受信宿主时间，不能来自记录自己的 accepted_at。

`observedScope` 必须由执行器从本次实际候选内容独立计算；不能复制承接记录的 scope 作为“观察结果”。校验器校验两侧结构、完整性和相等性，不证明调用方的实际取证行为。本轮没有可信证据解析、真实身份校验或文件权限装载入口，后续接线必须补齐；不得把返回的 `OWNER_ACCEPTANCE_METADATA_VALID` 改叫阶段 PASS。

### 条目摘要与最终内容 hash

`review_input_sha256` 是**审核前输入的摘要**，不能复用包含最终审核元数据的 `content_hash`，否则会形成“批准记录 hash 包含内容 hash，内容 hash 又包含批准记录 hash”的循环。

A2a 已实现 `owner_acceptance_review_input_sha256`：以既有 `content_governance_snapshot` 的标准化业务/来源/Question/scope/risk/effective 字段为输入，仅排除 `review_mode`、`primary_reviewer_id/role/review_evd`、`secondary_reviewer_id/role/review_evd` 七项；增加固定投影版本 `customer-agent/owner-acceptance-input/v1` 和 `script_version`，用既有 `jsonb_jcs` 计算 SHA-256。SQL/Node 合成对照已验证摘要一致，并逐个验证业务字段变化会改变摘要、审核元数据变化不会改变审核前摘要。输入闭合键集防止上游新增业务字段后被静默遗漏。

该函数接收**由既有函数产生的规范快照**，不是原始内容的完整业务校验器；现行内容/Question/scope 等验证仍须先执行。产品 loader 和仓外装包器尚未调用它，**还未证明实际候选正文与承接摘要一致**，不得复制批准记录里的摘要充当观察结果。

最终新版 content hash 仍应覆盖审核前输入、新承接模式、实际负责人/批准证据及承接记录摘要；历史版本与历史 hash 不重算。此处是第二批必须实现的合同要求，不表示当前 SQL 已支持。

### A2a · SQL 可信登记与撤销基础

- 候选 SQL：[owner-acceptance.registry.v1.sql](owner-acceptance.registry.v1.sql)。这是独立追加的本地候选，只在隔离 PG15 加载于 v1.14 之后，不是生产升级迁移；重复安装拒绝，不复用来源不明的已有角色。
- OpenAPI 扩展候选：[owner-acceptance.registry.v1.openapi-extension.json](owner-acceptance.registry.v1.openapi-extension.json)。这是待完整接线与版本化导出时合入的 vendor extension，不是独立 HTTP API、不新增 endpoint，也尚未合入当前 OpenAPI。
- `register_owner_acceptance` 重验精确记录字节 SHA、闭合结构、负责人、四域/条目/风险/期限，以及数据库中对应租户的不可变 canonical 来源摘要、复核日与停用记录。
- `app_owner_acceptance_registrar` 是 NOLOGIN 窄能力角色，只能登记/撤销，不能读写原表；普通 runtime/admin/import/work-order 角色无登记权限。它不是新增审批人，不要求第二个业务签字。真实登录角色绑定及包外批准证据核验执行器尚待产品/受控工具接线，不能用函数参数自行证明批准真实性。
- 记录与撤销均追加留存、租户 + 记录 SHA 绑定；UPDATE/DELETE/TRUNCATE 拒绝。相同登记、相同撤销可幂等重放；撤销异证据冲突，已撤销记录不可通过再次登记恢复。
- `assert_owner_acceptance` 是未授予任何应用角色的内部断言，精确比对实际 scope、主体、租户、用途、期限与撤销状态。它不执行发布、不切 current、不装包。
- 并发顺序固定为“既有来源治理锁 → 记录锁”；断言持共享事务锁，登记/撤销使用记录排他事务锁，来源停用复用旧合同的治理锁。断言与真正消费必须在同一事务，禁止断言后提交再使用。只接受 READ COMMITTED；拒绝可能遗漏新撤销证据的旧事务快照。已验证并发撤销等待/超时及来源停用冲突，不宣称完整产品并发验收。

## 4. 数据流与失败行为

```text
包外真实批准证据 -> 可信 record SHA + 负责人 + 宿主时间
                                 |
记录字节 -> hash 对比 -> 闭合结构/规范编码 -> owner/日期/风险校验
                                 |
实际候选 -> 独立审核前投影 -> observedScope -> 精确集合比对
                                 |
                  OWNER_ACCEPTANCE_METADATA_VALID
                                 |
                [产品接线尚未实现，保持旧门拒绝]
```

所有失败只输出固定错误码，不回显业务正文、内部链接、主体输入或 schema 的 data 内容。没有 fallback、自动补签、自动续期或部分放行。来源四域必须恰好各一条、版本 ID 不重复，条目 ID 不重复且来源域/版本一致；scope 的删项、换项、换版本或风险降级均拒绝。接受时间不能在未来；到期瞬间失效；记录不能晚于任一来源复核截止时间。真实包仍受独立 24h/清理合同约束，本记录期限不能放宽它。
