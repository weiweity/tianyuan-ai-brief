状态：APPROVED IMPLEMENTATION SCOPE（2026-09-06 用户授权按小功能逐 PR 推进）；只覆盖三处内容存储，完整 A2b 与真实准入仍未完成。

## 范围与边界方案

前置 PR #61 / #62 已提交且 CI 通过，尚未合并。本切片基于 PR #62 的候选核对，追加 `owner-acceptance.storage.v1.sql`；旧 v1.14 文件保持冻结字节。

比较“每行显式承接记录摘要”和“新增内容摘要到批准记录的映射表”：前者把批准来源随内容版本保存，没有新增并行状态所有者；后者会要求每次存储/复制同时维护映射。采用前者：scripts、staging_scripts、release_items 增加 nullable 承接记录 SHA；staging 增加仅承接模式必填的 script_version。旧 single/dual 的新增字段保持 NULL，历史摘要算法保持原样。

不能在发布时临时推算承接版本：批准记录与最终内容摘要都绑定版本。因此暂存时已固定它，后续发布消费者必须核对并传递该版本，不能沿用旧路径的无条件版本递增。

## 所有者与不变量

- `owner_acceptance_active_record` 统一拥有登记生命周期、时间、来源就绪、撤销、租户和事务锁；原整批断言改为复用它，再比对完整 observed_scope。READ COMMITTED、来源锁在前/记录锁在后的顺序不变，记录用途固定 g1a_offline_only。
- 一个纯 review-shape 函数供三表约束复用，保留历史合法 single/dual，新增承接模式要求无冲突、真实负责人和 EVD、非空合法记录摘要、空第二审核人。SQL NULL 明确失败关闭；风险类别、Question、范围、来源 FK、时间窗等独立业务检查继续保留。
- 一个写入 trigger 从 typed NEW 行调用既有 content_governance_snapshot，独立计算审核前摘要和最终 hash，再与登记记录中的条目和 EVD 核对。修改正文、Question、版本、来源、范围或风险后重算摘要仍不能借用旧批准。
- 租户来自内容所在位置：scripts.tenant_id、staging 的 import_batches、release_items 的 content_releases。该租户必须同时匹配不可变来源与承接登记；不按来源单方面推定消费租户。
- 逐行写入只证明“这是批准集合中的原样条目”，不证明批次没有删项。消费整批时仍须使用 A2b-2 的实际内容全量核对；不能用逐行通过替代整批通过。

## 权限、失败与阶段边界

所有新函数固定 search_path 并归 cs_ai_definer；新增内部函数无应用 EXECUTE，原表写权限不扩大。原已发布脚本保护、暂存生命周期和发布快照不可变约束保留；新锚点/版本变化必然影响最终摘要，受到实际行核对及既有内容保护。staging withdraw 要求新增字段也为空。

未登记、撤销、过期、来源暂停/跨租户、错条目/版本/摘要、未知审核形状全部拒绝；错误使用固定代码，不回显业务内容。测试 fixture 全为合成，数据库正常/中断清理沿用原 runner。

现有 finalizer、审核决策、发布/回滚和 current/readiness 还未统一接线，本切片不授予装包或运行权。不得将这份增量单独复制到产品迁移。后续必须完整转换消费接口、版本传递、批次精确集合、ACL 指纹、OpenAPI/DDL 导出后再交接产品。

## 设计复核与验证面

存储身份跟随内容行，生命周期判定不在各表重复实现；三表仅适配版本与租户位置。没有新增网络、缓存、连接池或后台服务。行写入执行来源/父记录和批准读取是防御性存储门的成本；未宣称批量性能验收，5000 条资源上限及整批校验继续由已批准合同约束。

验证覆盖三表合法 owner 及历史 single/dual 写入、重算摘要后篡改、错主体/锚点/第二审核人/冲突、缺失暂存版本、撤销/暂停、父/行租户错配、应用角色直写与私有函数拒绝、withdraw 新字段闭合。原登记/整批/并发撤销与隔离级别测试在新生命周期实现上重跑。
