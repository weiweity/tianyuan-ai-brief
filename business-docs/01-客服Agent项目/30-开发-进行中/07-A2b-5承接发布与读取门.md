# A2b-5 承接发布与读取门

状态：IMPLEMENTED CANDIDATE · SYNTHETIC VERIFIED。基于 A2b-4 / PR #65；仅合成合同实现，不表示正式运行、真实 G1a、T6 或部署放行。

## 范围与方案

复用 `publish_content_release`、`rollback_content_release`、`v_release_source_gate` 及现有租约/搜索入口。新建平行发布接口会复制 current、序号、质量、审计与租约协议，因此不采用。完整重定义既有函数而不改冻结 SQL，也不在安装时字符串替换 pg_proc。

新增内部函数分别隐藏两项不同的决策：

- `owner_acceptance_release_content_ready` 在发布/回滚写入边界，从实际 release_items 和独立 release_source_bindings 重建规范快照，检查最终摘要及每个承接记录的完整 scope。通过后才切换 current，失败保持整笔事务回滚。
- `owner_acceptance_release_ready` 服务读取。每个 persisted owner 行已由 A2b-3 写入门验证成员、正文、版本和审核字段；release_items 禁止 UPDATE/DELETE，且 release_id + script_id 唯一。因此按承接记录检查成员数等于批准成员数，再核对独立四域绑定和有效期/撤销即可证明集合完整，避免每次搜索重算整版正文摘要。新增成员仍经过原写入门。该推理不把绕过数据库触发器的超级用户篡改当成受支持运行方式。

两者复用 A2b-2/A2b-3 的有效记录与内容断言，不形成第二套批准解释。旧 single/dual 不引入新版摘要。新内部函数均不授予应用角色；现有函数签名、owner 和应用 ACL 保持不变。

## 写入和读取不变量

- 发布重验暂存版本仍为 authoring 后继版本；新增、冲突更新和 release snapshot 均传递同一承接锚点及批准版本。
- 租户从已锁批次/目标 release 取得；禁止跨租户的 current、authoring 或新绑定来源。归档仅作用于该租户，避免继续写死 `default`。
- 旧记录过期或被撤销后仍能归档 authoring；仅允许 status/updated_at 变化，正文、身份和版本不能趁归档改写。恢复 published 或其他修改仍经过完整存储门。
- 回滚复制不可变目标的版本、摘要和承接锚点，在目标读取及新快照生成后均核对；不重算/改写历史版本，不使已撤销/过期承接复活。
- current、搜索、离线租约、snapshot page 和 ACK 经既有 source gate 收到承接有效性判断；拒绝仍使用现有运行层 `SOURCE_GATE_NOT_READY`，内部 gate reason 可为 `OWNER_ACCEPTANCE_NOT_ACTIVE`。
- 离线租约截止时间取请求 TTL 与该 release 最早承接截止时间的较小值。已发租约在线使用时仍重验承接；离线端无法实时获知新撤销，原离线租约期限风险没有被本功能消除。
- 成功读取保持来源/记录共享事务锁；并发撤销和来源停用须等待。非 READ COMMITTED 的 owner 读取拒绝，不能让旧事务快照漏看新撤销。

## 精确批准与质量隔离

负责人承接不替代独立质量证据。若同一承接 scope 同时含 clean 和 quarantined 条目，发布只选择 clean 后将不再满足完整批准集合，必须拒绝；不能静默缩小 scope 或伪造新批准。需要发布子集时，应由受控批准流程提供与实际子集匹配的新记录。

本合同继续只接受 `g1a_offline_only`。SQL 内部一致性不证明登记调用方已取得真实批准或满足隔离条件；真实证据适配器、产品受锁快照及运行隔离由后续产品接线完成，正式运行门未放宽。
