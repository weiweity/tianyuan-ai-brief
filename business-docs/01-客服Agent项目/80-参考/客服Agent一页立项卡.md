## 这次会要解决什么

不是讨论“项目做不做”，也不是让客服人员选择技术框架。会前先填事实，60 分钟内逐项处理下面 9 件事；没有证据的事项不硬定：

1. 一期先解决哪个真实、高频客服问题；
2. 谁是主要使用者、在哪个平台工作；
3. 软件一期帮到哪一步、明确不做什么；
4. 什么指标改善才算成功；
5. 哪些错误、安全、稳定或费用情况必须停止；
6. 正确答案或业务依据来自哪里，冲突时听谁；
7. 先由哪 3–5 名坐席试用；
8. 后续预计多少人使用，有没有高峰；
9. 项目、业务、内容、验收、预算、IT / 安全分别由谁负责。

## 会前请带什么

| 角色 | 请准备 |
|------|--------|
| 客服总监 / 经理 | 当前核心指标、最想改善的业务结果、试点团队与预计人数 |
| 一线坐席 | 2–3 个脱敏真实任务：怎么做、耗时多久、哪里返工或升级 |
| 客服 BP | 当前流程、跨团队依赖、历史问题与可用数据 |
| 内容 / 数据负责人候选 | 权威文档或系统、权限、更新时间、冲突规则与维护人 |
| 项目负责人 | 会议记录模板、九项决定表、OPEN / Owner / 截止日 |

没有分母、样本或来源的数据登记为 `OPEN（待补证）`，并同时写负责人和补齐日期。

## 60 分钟怎么走

`0～5 边界与分工 → 5～15 真实任务 → 15～23 主问题 → 23～30 一期边界 → 30～38 成功 / 停止 → 38～45 真源 / Owner → 45～52 试点 / 人数 → 52～60 决定回读`

最后 8 分钟不挪用。技术栈、API、容量阈值、费用数字和超时讨论进入停车场，会后由工程或对应负责人书面答复。

会中只记四种状态：`DEC（已决定）`、`PRECONFIRM（会前已填、现场待确认）`、`OPEN（待补证）`、`PARKING（不在本会决定）`。

## 一期边界

**一定保留：** 系统辅助，坐席核对，人工处理，记录结果。

**明确不做：**

- 自动代发或自动接管客服会话；
- 四个候选方向同时开发；
- 在会上用投票代替业务负责人决策；
- 让客服人员选择编程语言、数据库或 AI 框架；
- 把供应链工作塞进客服一期；
- 复用任何早期学习项目的代码、数据、配置、账号或部署；
- 把已收尾的汇报 Web 当生产产品继续改。

知识 / 话术辅助、智能质检、反馈分析、聊天分析只是理解问题的讨论起点，不是预设答案。

---

## 会后怎么判断

会议结束时，九项决定必须各有状态；每个非 `DEC` 项都要登记原因、唯一负责人、截止日和证据位置。需求会完成不等于开发开工；只有 G0 全部证据通过并正式签发 Ddev，才创建产品代码和开发任务。
