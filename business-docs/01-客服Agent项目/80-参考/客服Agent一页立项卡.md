## 这次会要解决什么

不是讨论“项目做不做”，也不是让客服人员选择技术框架。项目侧带来一个待校准的建议：先解决商品 / 活动话术分散、难检索、版本与有效期难确认的问题；软件展示证据，信息不足就澄清，有冲突、过期或无依据就升级，坐席人工确认并发送；灰度前先做历史问题影子回放。客服可以确认、修正或否决。

会前先填事实，60 分钟内逐项处理下面 9 件事；没有证据的事项不硬定：

1. 客服是否确认、修正或否决项目侧一期主问题；
2. 谁是主要使用者、在哪个平台工作；
3. 软件一期帮到哪一步、明确不做什么；
4. 什么指标改善才算成功；
5. 哪些错误、安全、稳定或费用情况必须停止；
6. 正确答案或业务依据来自哪里，冲突时听谁；
7. 2 新手 + 2 老手候选是否覆盖平台、意图、班次、活动期和风险；不足时如何增补或替换；
8. 后续预计多少人使用，有没有高峰；
9. 项目、业务、内容、验收、预算、IT / 安全分别由谁负责。

## 60 分钟怎么走

`0～5 启动目标 → 5～15 真实任务 → 15～23 校准建议 → 23～30 一期边界 → 30～38 成功 / 停止 → 38～45 内容依据 → 45～52 试点 / 环境 → 52～60 结果 / 下一步`

最后 8 分钟不挪用。技术栈、API、容量阈值、费用数字和超时讨论进入停车场，会后由工程或对应负责人书面答复。

会中只记四种状态：`DEC（已决定）`、`PRECONFIRM（会前已填、现场待确认）`、`OPEN（待补证）`、`PARKING（不在本会决定）`。

## 一期边界

**项目侧建议保留：** 展示候选话术及来源、版本、平台 / SKU / 活动有效期；信息不足先澄清，冲突、过期或无依据时升级；坐席核对并人工发送；记录采用、修改、拒绝、未命中和最终结果。

**明确不做：**

- 自动代发或自动接管客服会话；
- 订单、物流、退款和售后系统深度集成；
- 多个方向同时开发；
- 在会上用投票代替业务负责人决策；
- 让客服人员选择编程语言、数据库或 AI 框架；
- 把供应链工作塞进客服一期；
- 复用任何早期学习项目的代码、数据、配置、账号或部署；
- 把已收尾的汇报 Web 当生产产品继续改。

一期人数很少，只做新手和老手各自的匹配任务探索性比较，不宣称统计显著性；环比只作辅助趋势。正式同期分层 A/B 放到二期。
