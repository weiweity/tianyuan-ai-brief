# 客服 Agent · 一期启动会方案收口验收

> **验收日期：** 2026-08-03
> **验收对象：** 客服 Agent 一期启动会故事线、一期方案、三阶段路线、试点与评测设计
> **当前状态：** **PRECONFIRM · 项目侧建议，待客服在启动会确认 / 修订 / 拒绝**
> **会议结论：** 材料可用于启动会讨论和形成业务决定；**项目批准不等于开发开工、灰度测试或上线许可**。
> **证据边界：** 本文是带日期的方案收口快照，不替代 `00–06` 业务真源、正式会议决定、G0 签发或真实试点验收。

---

## 1. 收口结论

当前建议以客服已经发生的真实困难为起点：坐席需要跨多张飞书在线表检索产品和活动话术，语义检索困难时不敢确认答案，只能询问资深客服、话术师或兼职培训师；夜间可能等待较长时间，人员更替后还会重复培训，并存在使用过期话术的风险。

基于该问题，一期项目侧建议为：

> **证据型客服助理 + 灰度前影子回放。** 先帮助坐席找到可追溯、版本有效的候选答案，由人工确认后使用；先验证“能否更快找到、是否敢确认、依据是否正确”，不自动代发，不把一期包装成完整客服 Agent。

该建议已完成项目侧方案收口，状态仍是 `PRECONFIRM`。启动会必须允许客服基于真实工作事实做三种处理：**确认、修订或拒绝**，不能把会前方案直接记为业务决定。

## 2. 三阶段路线与一期边界

| 阶段 | 目标 | 当前承诺边界 |
|---|---|---|
| 一期 | 3–5 名内部坐席灰度验证；建议先覆盖产品话术与活动话术，验证证据型辅助闭环 | 人工确认、只给候选答案和来源；不自动发送，不承诺全量上线，不宣称客服 Agent 已完成 |
| 二期 | 扩大 / 全量测试；重点完成数据清洗、语料库蒸馏、软件稳定与缺陷修复 | 在指标字典、样本和实验协议冻结后，再开展正式 A/B 或准实验评估 |
| 三期 | 在前两期证据、语料和稳定性成立后铺设客服 Agent | 是否进入三期由前期真实结果另行决策，不在本次启动会预先批准 |

一期最小闭环建议为：

```text
坐席输入真实问题
  → 系统给出候选话术、权威来源与版本提示
  → 坐席确认、修改、拒绝或升级人工
  → 记录问题、候选答案、依据、坐席动作和结果
  → 用真实记录改进检索、内容治理与后续语料
```

## 3. 试点与比较设计

一期建议先以 **2 名新手 + 2 名老手** 组成首批比较样本；若增加第 5 人，应优先补齐业务覆盖，而不是为了凑人数。这里的“新手 / 老手”须在 Pilot Ready 前由客服给出可执行定义，不直接用未经确认的入职年份阈值代替业务判断。

| 比较 | 目的 | 一期如何解释 |
|---|---|---|
| 新手内部配对 | 看辅助工具是否减少跨表查找、求助和犹豫 | 同类任务、同一时段或可比时段下做描述性配对，不宣称统计因果 |
| 老手内部配对 | 看工具是否减少重复检索，并保持答案质量 | 分开报告，避免老手经验掩盖新手收益 |
| 使用者环比 | 看同一坐席使用前后的趋势 | 同时记录活动、大促、班次、问题难度等干扰因素 |
| 覆盖优先 | 避免只测容易问题导致虚高 | 产品 / 活动话术与高风险负例均需覆盖；缺少真实样本时保持 `OPEN` |

一期是小样本灰度验证，适合报告命中、时长、求助、修改、拒绝 / 转人工和异常分布，**不把它称为正式 A/B 实验**。二期扩大样本后，才冻结分流、分层、实验周期、污染控制和显著性口径，并评估是否采用 A/B、差分中的差分或其他准实验方案。

## 4. 指标与风险口径

启动会只需要确认“为什么要测、从哪里取数、由谁负责”，不能在没有基线时编造目标值。

建议指标分为四组：

- **效率：** 单次查找 / 处理时长、跨表次数、群内求助率、等待时长；
- **质量：** 来源与版本正确、坐席修改率、拒绝 / 转人工率、过期话术使用情况；
- **体验：** 新手与老手分别报告敢确认程度、可理解性和使用负担；
- **稳定与安全：** 失败率、回退可用性、越权承诺、敏感信息和高风险错误直答。

中国电商客服环境下，评测集至少覆盖六类风险：**信息不足、内容冲突或过期、跨平台规则差异、SKU / 商品识别错误、越权承诺、敏感信息**。每类样本量、停止阈值和恢复条件仍需业务、安全及工程共同确认。

**指标字典和最低有效配对数必须在 Pilot Ready 前冻结。** 当前文档给出的是测量框架，不代表指标分母、目标值、样本量或停止线已经批准。

## 5. 当前门禁快照

| 门禁 | 当前值 | 允许做什么 | 明确不允许 |
|---|---:|---|---|
| 项目批准 | 已有受控批准证据 | 召开启动会、补证、收敛方案 | 推导为技术栈、费用、开发或上线已批准 |
| 跨团队责任 G0 | **1 / 14 Pass** | 分配责任人、证据和截止日 | 宣布 G0 已签发 |
| Scope 检查 | **1 / 15 Pass** | 讨论一期范围、验收和停止条件 | 宣布范围已冻结 |
| Ddev | **未成立** | 做需求、数据、安全和技术准备 | 编写 / 合并产品功能代码或宣布开发开工 |
| 灰度 | 未获许可 | 设计试点、准备评测协议 | 部署、培训、真实放量或承诺上线 |

因此，本轮验收只给出“**启动会材料可用**”结论，不签发开发、Pilot Ready、灰度或生产许可。

## 7. Office Hours 三轮评审

本方案经过三轮 Office Hours 评审与修订，最终为 **9.2 / 10**，不是 10 分。

| 评审重点 | 收口结果 |
|---|---|
| 问题是否真实、足够具体 | 从“降低人力成本”的宽泛目标，收敛到跨表检索、隐性知识求助、夜间等待、重复培训和过期话术风险 |
| 一期是否过度画饼 | 将一期限定为证据型辅助与小样本灰度，客服 Agent 明确放在三期；同时保留为二期数据清洗和语料蒸馏铺垫 |
| 测试是否经得住反驳 | 新手 / 老手分层、组内配对、使用者环比、覆盖优先；一期只做描述性证据，不冒充正式 A/B 因果结论 |
| 是否适合电商客服环境 | 补齐产品 / 活动话术、跨平台、SKU、越权承诺、敏感信息和大促 / 班次等干扰因素 |
| 是否具备开工条件 | 否；G0、Scope、指标字典、最低有效配对数和外部证据仍未冻结 |

剩余 `0.8` 分不是文案润色问题，主要来自尚未发生的业务确认、真实数据、责任具名、实验参数冻结和会场 / 平台验证。不得通过提高静态自评分来掩盖。

## 9. 最终判定

- **GO：** 使用当前材料召开客服 Agent 一期启动会，向客服讲清真实问题、一期建议、三阶段路线、试点方法和待确认事项。
- **PRECONFIRM：** “证据型客服助理 + 灰度前影子回放”仍是项目侧建议；客服可以确认、修订或拒绝。
- **NO-GO：** 不允许将本次收口解释为 G0 / Scope 已通过、Ddev 已成立、技术栈已选、产品代码可开工、灰度已批准或客服 Agent 已上线。
- **下一门：** 补齐外部 OPEN，并在 Pilot Ready 前冻结指标字典、最低有效配对数、停止 / 恢复规则和真实试点协议。
